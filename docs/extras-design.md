# 扩展能力（extra）设计

> 2026-10-15 落地并同日扩了一轮（命令装载 / 提示词注入 / 接管模式）。本文记录**已经实现**的形态与它的取舍，不是提案。
> 相关：`AGENTS.md`「扩展能力（extra）」、`docs/ts-migration-plan.md` §2。

## 1. 要解决的问题

`src/extra/` 用来收"额外且相对独立的功能"。在这之前，加一个能力要在四处装配点各改一次（工具表、装配清单、描述表、组装根），而它本来只该是"多一个工具、或者多一个后台任务"。扩展层要做的就是把这件事压成**建一个目录 + 加一行**。

同时它要满足两个要求：**不用的时候不付代价**（不起子进程、不占内存），以及**装载的时机由人决定**（见下一节）。

## 2. 谁能装载 —— 这一节是全部设计的地基

**模型一个装载入口都没有。**

- 装载与卸载的唯一入口是主流程那条 `/能力` 命令：`/能力`（看列表）、`/能力 加载 <id>`、`/能力 卸载 <id>`，外加配置 `extras.override` 在启动时播种。
- **群里的斜杠命令要先 @ 机器人**：主流程那四条（`/能力` `/转写` `/画` `/漫画`）**一律要**，扩展自己的命令由 `ExtraCommandSpec.requiresMention` **逐个声明**（缺省 `true`；`clock` 要 @、`trpg` 那族显式 `false`）。私聊恒不生效。判据读的是 ingest 从**原始段**算出来的 `mentionedSelf`，**不是文本** —— 开头那串 @ 已经被掐掉了（见 §3.4 末尾）。**没 @ 就压根不是命令**（返回 `false`，消息照常落档、照常参与响应判定），不是"认出但拒绝"。回执里**不把 `@我` 拼进命令行**（那是示意，不是能敲的文本）。
- **敲扩展自己的命令不再把它拉起来**（2026-10-19，用户要求）：未加载时命令照旧**认得出**（消息落成已读、不惊动模型），但只回一句「先 /能力 加载」。判据静态是为了**不静默**，不是为了隐式装载。
- **未装载的扩展，它的工具不在工具表里**。模型连"有这个能力"都看不到，更没有"调用即加载"这条隐式路径。

这条取舍带来一串必须一起成立的性质：

| 性质 | 为什么必须这样 |
|---|---|
| **工具表按"已装载"、命令表按"已启用"** | 两个入口的人不同：命令的入口是**人**（判据按 spec 静态，敲得到），工具的入口是**模型**（只该看到此刻真正可用的能力）。这条**不对称是刻意的**，别统一掉 |
| **命令的判据留在 `spec.ts`** | `isCommandEntry()` 是同步的、且在入站热路径上被调（决定 `wakeEligible`、要不要并入引用附件）。它不可能去问一个异步的装载表 —— 判据静态（认得出），而装载在**另一处**（`/能力 加载`），矛盾就没了 |
| **别名由分发层统一处理** | 见 §3.3 |
| **`/能力` 在任何模式下都存在** | 它是解除接管的唯一入口。把它一起换掉就是死锁（装得上、卸不掉） |
| **接管按会话隔离**（§6） | 附加是全局的、接管只作用于它绑定的会话 —— 所以三张表都按会话算 |
| **拦消息 = 越过模型回复**（§3.5） | 纯工具能力当场回话，那一轮模型调用根本不发生。所以那条消息必须落成**已读**历史 —— 落成未读就会反过来把它唤醒 |
| **配置覆盖只作用于一次运行**（§3.6） | `getConfig()` 是全局的、没有会话上下文，所以覆盖**不能**做进它里面；只在 `runAgent` 开头叠一份新的，那一轮读它 |
| **工具表变成运行期可变** | `agent-runner` 每次运行开头读一次 `host.toolDefs`（`WakeScheduler` 上是 getter），语义因此是"**装载后，下一次运行生效**" |

**代价（知情）**：tools 是请求前缀的一部分，装载/卸载各打散一次提示词缓存。但频次由人控制（TTL 默认 10 分钟），这正是这条设计换来的东西。

**开放问题**：`/能力` 的权限与内置命令一致（白名单会话里可敲，群里还要 @ 机器人），所以白名单群里**任何群友**都能起一个重扩展 —— **@ 只挡住手滑，不是权限**。缓解是 `extras.maxLoadsPerHour` 那道闸门；要收紧只需在 `commands.ts` 那一处加判据（仓库目前没有"管理员 QQ"的概念，管理动作的既有落点是 HTTP 控制台）。

## 3. 形态

```text
src/extra/
├─ types.ts          契约（ExtraSpec / ExtraRuntime / ExtraCommandSpec / ExtraPromptContribution）—— 不 import 本模块任何文件
├─ prompts.ts        扩展的固定指令 EXTRA_PROMPT_TEXT / EXTRA_PROMPT_SECTIONS / EXTRA_PROMPT_JOBS —— **必须无 import**（§7）
├─ registry.ts       静态清单 EXTRA_REGISTRY，每行 { ...xSpec, load }
├─ runtime.ts        ExtrasRuntime：装载表 + 由它派生的三张表 + 校验 + 运行结束钩子
├─ clock/            参考扩展（attach）：把整条链跑起来并可观察，刻意只有最小形态
└─ trpg/             第一个功能完整的**接管**扩展（override）。目录内部按职责分：
   ├─ spec.ts        纯数据（4 个工具 + 2 条命令 + overrideTools）
   ├─ impl.ts        createRuntime(deps)：只做接线（handlers / commandHandlers / prompt / onRunEnd）
   ├─ state.ts       状态层：上限、归一化**含旧形状迁移**、读写（`data/trpg/<会话>.json`）+ `safeFileName`
   ├─ rule-store.ts  规则表存储（`data/trpg/rules/`，种子懒补齐、坏表拒绝、按 mtime 缓存）
   ├─ scenario.ts    剧本存储（`data/trpg/scenarios/`，极简 frontmatter 解析 + 同一套归一化）
   ├─ render.ts      展示层：给模型的状态段 / **给群友的玩家视角**（两份独立函数）/ 掷骰与检定的结果格式 / 清单+剧本那一段
   ├─ tools.ts       4 个工具的实现（校验 → 改状态 → 把"发生了什么"回给模型）+ 行动经济账本
   ├─ suggest.ts     DM 整轮沉默时的兜底建议（生成 + 解析）
   ├─ entropy.ts     唯一熵源（`node:crypto`）—— 规则层不许 import 它，由调用方注入
   ├─ types.ts       领域类型 + `HIDDEN_FIELDS`（**不 import 本模块任何文件**，防成环）
   └─ rules/         纯函数规则引擎（dice.ts / percentile.ts / condition.ts / check.ts / economy.ts），**与对话链完全无关**
```

**宿主递给扩展的口子**（`ExtraRuntimeDeps`，§7 与 `types.ts`）：`load(deps)` 收下它，成员**全是可选的**，缺省时那条路退回同步/降级行为。当前五个：`deliverNote(chatKey, note)`（把一条机器条目送进会话）、`sendPrivate(targetUserId, text)`、`sendFile(chatKey, fileName, content)`、`sendText(chatKey, text)`（2026-10-19 加：**往会话里补一句话** —— 命令的返回值只够回一句，而 `.trpg scenario` 要在"开始做"和"做完了"各说一句）、`recordUsage(usage)`。⚠️ **`deliverNote` 与 `sendText` 的收件人不同**：前者是给**模型**的机器条目（落存档、入窗、唤醒一次运行），后者只是发给群里的一句话（模型不因此被叫醒）。**为什么是参数而不是让扩展自己 import**：那条链要碰 `ChatStore` 与 `Orchestrator`，而 `extra → agent` 是反向依赖（层级闸门会拦），组装是 `web/` 的活。扩展只说"这是一条什么、正文是什么"，**怎么落库由宿主决定**。

```ts
// registry.ts —— 与 web/runtime/lifecycle.ts 的装配清单同一形态：存函数引用、只 for...of、无按键分发
export const EXTRA_REGISTRY: readonly ExtraEntry[] = [
  { ...clockSpec, load: () => import('./clock/impl.js').then((m) => m.createRuntime()) },
  { ...trpgSpec,  load: (deps) => import('./trpg/impl.js').then((m) => m.createRuntime(deps)) }
];
```

⚠️ `load` 的参数列表允许有内容（`(deps)`），但**说明符必须仍是字面量** —— 写成变量就搬不进包，`t-extras.mjs` 有一条源级断言钉这两件事。

**加一个扩展 = 建一个目录 + 在本文件加一行。** **顺序是语义**（`/能力` 的列表与"命令表第 0 条是谁"都按注册表顺序），新扩展加在末尾。

**接管扩展多写一个字段**：`overrideTools: { sendTool, finishTool }`（见 §5）。**attach 模式写了它会被拒绝装载** —— 没有任何地方读它。

### 3.1 声明与实现分开

`spec.ts` 被注册表**静态** import，`impl.ts` 永远走 `import()`。

`ExtraRuntime` 提供 `handlers`（工具名 → 执行函数）、可选的 `commandHandlers`、可选的 `prompt(chatKey)`、可选的 `toolsFor(chatKey)` 与可选的 `dispose()`。

**`toolsFor(chatKey)`：一个扩展按会话说"我此刻露哪些工具"**（2026-10-16 加）。不写 = `spec.tools` 全部。跑团用它实现"**助手模式只暴露骰子**"—— 同一个扩展，一个群当骰子机器人、另一个群当 DM。三条边界：**只能返回声明过的名字**（多出来的被 `toolDefs()` 滤掉并记日志，不抛 —— 这是运行期、在别人的一轮对话里被调的）；**必须收 `chatKey` 且必须是全函数**（装载时会空着会话调一次，抛了就等于拒绝装载，而症状是"这个扩展装不上"，与工具表毫无关系）；**它让工具表按会话变化**，切换形态打散一次提示词缓存（频次由人控制）。判据与 `Override` 那条同源：**模型看到的与它真能用的必须是同一套东西** —— 留着两个用不上的工具、只在提示词里求模型别调，等于每轮多花一段前缀、还给它一次调错的机会。

**为什么是"名字 → 函数"的映射而不是单个 `execute(name, …)`**：只有这样名字集合才**可枚举**。写成单个 `execute` 的话，运行时无法在不真的执行一次的前提下知道实现认哪些名字，那句"装载时校验声明与实现对得上"就只能退化成"凭声明相信它" —— 而声明与实现分居两处，正是这套设计唯一的漂移点。查表本身**不是**被禁的"字符串式业务注册表"：它是扩展自己实现的内部细节，键来自 `spec`（注册表静态数据），不参与任何跨模块分发。

### 3.1.1 命令这一侧的两个形状 —— 一个必须分开，一个必须合并

| 形状 | 住哪儿 | 是什么 |
|---|---|---|
| `CommandEntry`（内部） | `web/onebot/commands.ts` | **命令骨架**：`run(input, deps): Promise<void>`，回执发送 / `error.message` 原样进群 / 发送失败不抛三条都在它的 `runCommand` 外壳里 |
| `ExtraCommand` | `extra/types.ts`（**唯一定义处**） | **业务实现**：`run(input): Promise<string\|null>`，只返回一句回执文本，**不碰 sender** |

**必须分开**：两者职责不同 —— 骨架管"怎么发出去"，实现管"发什么"。`adaptExtraCommand()` 就是把后者套进前者的那一层。

**必须合并的是它自己的定义处**：`ExtraCommand` 只写在 `extra/types.ts`，web 侧 **import 它**（`web → extra` 是允许的方向），不再抄一遍形状 —— 抄一遍的话"两边漂移了"只能靠人核对，import 之后**编译器就会报**（`adaptExtraCommand` 里那句 `command.run(input)` 就是那条编译期对账）。

### 3.2 三张表各自的筛选条件

三张表**都按会话算**（接管是按会话隔离的，见 §6）：

```ts
toolDefs(chatKey)     // 接管中：只有接管者的；否则：**已装载**的附加扩展
commandDefs(chatKey)  // 接管中：只有接管者的；否则：**已启用**的附加扩展（接管的命令不外泄）
promptPlan(chatKey)   // 接管中：它的 body；否则：已装载附加扩展的 append/override
```

**两种模式的释放时机不同**（`extras.idleUnloadMs`，`0` = 不限）：

- **附加**：到点**卸载实现**。
- **接管**：到点**那个会话交还主流程**；实现由别的绑定或附加装载继续养着，**最后一个绑定走掉时才 dispose**。

### 3.3 命令的词形列表

一条命令只声明**一个词形列表** `names`（第一个是主命令词），例如 `/能力` 是 `['/能力', '/扩展']`、参考扩展是 `['/时间', '/time']`、`/转写` 是 `['/转写']`（`/转写[视频]` 那条特例词形已被边界规则取代）。

```ts
matchesCommand(cmd, text) = cmd.names.some((w) => startsWithWord(text, w))
canonicalize(cmd, text)   = 命中**非首位**词形时，把开头那个词换成 cmd.names[0]
```

**判定、规范化与日志标签三样都从这一个数组派生**，没有第二种判据：

| 用途 | 取自 |
|---|---|
| 认不认这条消息 | 任何一个词打头 |
| 交给 `run` 的文本 | 命中非首位词形时**换回 `names[0]`** |
| 日志标签（失败时那句 `[/转写] task=…`） | `names[0]` |
| `commandHandlers` 的键（装载时两个方向对账） | `names[0]` |

**为什么必须规范化**：每个命令的解析器只认识自己那一个词。不换的话，加一个词形要同时改解析器 —— 内置的解析散在 `media/` 下各能力里、扩展的在 `impl.ts` 里，三处各改一次，而漏改的表现是"命令被认出来了、但参数解析不出来"（`/time` 交给只认 `^/时间` 的解析器 → 返回一句用法提示）。

**⚠️ 这三样曾经是三份定义**：`name` + `aliases` + 一个 `match(text)` 正则，而正则里也写着 `/画` —— 改一处忘一处不会有任何报错。合并之后，`t-commands.mjs` 有一条源级断言钉住"命令对象上不许再出现 `match`"。

**推论：`names[0]` 必须是真能敲的那个词。** 曾经内置命令写的是 `'transcribe'` 这类内部标签，规范化一接上就把它变成了 `transcribe …`，解析器当场认不出来 —— 这是实测踩到的一次。

所有词形**共用一个命名空间**（同一个命令内部、不同命令之间、跨扩展都查），注册表自检拒绝重复：重了的话"先匹配到的先处理"会静默地决定谁赢，而两个命令的作者都以为自己的那个会被执行。

### 3.4 边界：`词` 后面跟空白、`[`、或直接结束

`startsWithWord` 的规矩是**一条**（所有词形共用）：`/画像` 不是 `/画`，`/weatherx` 不是 `/weather`，`/画廊今天开了吗` 不是 `/画`。

**为什么 `[` 也算边界**：协议端把媒体/卡片段渲染成**紧贴着**的占位符（`segmentsToText` 用 `out.join('')`，没有分隔符），所以"发一个视频 + 打一句 `/转写`"送来的文本是 `'/转写[视频]'` —— 中间没有空格。不放宽这一条的话，这类消息**根本认不出来**：

- 它会被当成普通消息**进 LLM**（`wakeEligible` 也跟着变 `true`），白多花一次模型调用，而且**不报任何错**；
- 而它恰恰是 `/转写` 最常见的一种用法（直接丢个视频 + 打命令，不用引用）。

**曾经的写法是给 `/转写` 单开一个 `/转写[视频]` 词形绕过它** —— 那是一条**特例**，而特例的问题是每多一种渲染形态就要多一条（`[图片]`／`[语音]`／`[表情1]`／`[文件x]`…）。统一成边界规则之后，那条特例被删掉了，`/画[图片]`、`/漫画[图片]` 这些同形的也一并认出来（它们会回一句用法提示，比默默进 LLM 好）。守护是 `t-commands.mjs` 里的一条源级断言：**`/转写[视频]` 不许再出现在词形列表里**。

⚠️ **只放宽到 `[`**，不是"任何非字母数字"：`@`（@ 段也紧贴）不在内 —— `/画@某人` 更像误触；再宽一点就会把 `/画xx` 那类既要拦住的也放进来。

**另一头（2026-10-19 加）：命令前面那串「@机器人自己」的段由 ingest 先掐掉**（`stripLeadingSelfMentions`），所以 `@bot /能力`、`@bot 3d6` 都照常命中 —— 掐的是**命令判定用的那份文本**（`commandText`），进存档的 `text` 仍带着 @。只掐**指向机器人自己**的那一串（比对 `onebot.selfId`，为空时不掐）：`@小明 /画 猫` 是在跟别人说话，顺手把命令执行掉是误伤。实测成因与四条边界见 `docs/ts-migration-plan.md` §8.1。


### 3.5 拦消息（`intercept`）：纯工具能力越过模型回复

斜杠命令已经是一条确定性快路径，但它要求群友**先敲斜杠**。这个钩子让扩展认下**普通消息**：一个骰子机器人可以直接接住 `3d6+2` 并当场回话，**一整轮模型调用都不发生**。没有它的话，这类消息只能靠模型判"这看起来像个骰子表达式"再调工具 —— 慢、要花钱，而且受响应档位约束（把参与度调低的群里，连 `3d6` 都不会理）。

```ts
intercept?(input: ExtraCommandInput): ExtraInterceptResult | null
// null          → 不管这条，照常走模型
// {}            → 拦下但**不吭声**（屏蔽 / 去重）
// { reply: '…' } → 拦下，由宿主把这句话发进群
```

- **入参就是命令那个形状**：一条入站消息 + 它的媒体。**只含本条自己的媒体**，不含它引用那条的 —— 合并引用附件是给"附件型命令"（转写 / 画）准备的，而拦截是纯文本判断。
- **必须同步、无 I/O**：它跑在**每一条**入站消息上。一个会 `await` 的实现会把整条入站链拖慢，而它自己看不出慢在哪里。要干慢活就入队（像 `/画`）。
- **必须在落档之前判**：落档要带 `wakeEligible`。拦下的消息**照常存档、照常上面板**，但落成**已读**历史（与斜杠命令逐字同形）：模型以后在【过去状态】里读得到，这一轮不惊动它。不落档会让面板与存档从此不一致；落成未读则当场与"越过模型"自相矛盾。
- **问谁**与工具表同一套判据：附加模式要装载过，接管会话只问接管者；顺序即优先级，取第一个说"我要"的。
- **抛错被吞掉并记日志**（运行时那层），绝不把异常打进 OneBot 的入站回调 —— 它跑在每一条消息上，一个写坏的钩子不该让人连聊天都收不到。
- **`{}` 是"全拦"那一档，跑团的助手模式正靠它**（2026-10-16）：认不出骰子的消息也一并拦下，于是那个群里**一次模型调用都不会发生**。它顺带推翻了一句早先的结论 —— "助手模式仍受响应档位约束"不再成立：拦下的消息与斜杠命令逐字同形（`wakeEligible: false`、落成已读），窗口判定**根本走不到它**，所以低档位群里照样掷骰。**代价是知情的**：`3d6x`（敲错）与 `3d6 帮我看看`（半句话）都得不到回话（判据是"整串就是一个合法表达式"，放宽就会把后者变成一句语法错误）。

### 3.6 运行期配置覆盖（`configPatch`）：只叠在"这一轮运行"上

```ts
configPatch?(chatKey: string): ExtraConfigPatch   // 形状同 data/config.json
```

`agent-runner` 开头调一次 `host.configFor(chatKey)`，把全局那份叠上本会话里可用扩展的补丁，**这一轮读到的每一处配置都是叠过之后的**。

- **不落盘、不外溢**：走 `core/config.ts` 的 `mergeConfigPatch`（新的纯函数：叠 + 归一化，**不改全局**）。改全局只有 `updateConfig` 一条路。于是"接管 A 群的扩展"不会顺手改掉 B 群的行为，并行的两个会话各看各的。**这是它最容易被人误解的一点** —— 实测探针：把 `mergeConfigPatch` 换成顺手 `Object.assign` 写回全局，`t-extras` 立刻报出 `{"maxRounds":42,"idle":999999999}`，那正是外溢的样子。
- **⚠️ 必须一路传到提示词拼装里，否则只生效一半**：`buildSystemPrompt` / `buildUserPrompt` / `buildPastState` / `formatEntry` / `triggerLabels` / `digestConfigForChat` 都收一个 `config` 参数（缺省 = 全局那份，既有调用点逐字不变），**内部一律不再自己读 `getConfig()`**。分两处读的话，"预算 / 摘要档位 / 表情档位 / 成员备注"那一半就还是全局的，症状是"覆盖了、只生效一半"，没人查得出来。
- **它管不到整条链路**（如实记下）：入站白名单、发送限频、面板显示、以及**工具定义本身**（`buildToolDefs()` 在 app 启动时算一次）读到的仍是全局那份。`resolveTranscriptionConfig(cfg)` / `resolveImageGenConfig(cfg)` 收的是 `cfg`，**在**范围内。
- **上下文窗口容量与历史深度曾经也管不到，2026-10-16 起管得到了** —— 那是**改了两个读取点**换来的（不是它自己长出来的）：① `Orchestrator` 建 `ContextWindowRegistry` 时按 `configFor(chatKey)` 取容量（`capacity` 因此从"数字"变成 `数字 | ((chatKey) => number)`，`capacityFor(chatKey)` 是唯一入口）；② `wake-scheduler` 算历史深度时读 `this.configFor(chatKey)`。**两处缺一，症状都是"配了、看着生效、实际用的是别的"**：只改第一处，窗口宽了而【过去状态】还是老的深度；只改第二处，反过来。探针实测：把第一处退回全局读 → `t-trpg` 红 1 条 + `t-window` 红 2 条；把第二处退回 → `t-trpg` 红 1 条（**只有**历史深度那条，容量那条照样绿）。跑团用它把"够跑一局"的三个数（`maxContextMessages` / `historyCount` / `promptContextMaxChars`）抬到 `CONTEXT_FLOOR`，**语义是下限不是覆盖**，且 `0`（不限）原样留着。
- **响应档位 2026-10-19 起也管得到了**，那是**第三个读取点**：`wake-scheduler` 的 `#resolvePendingResponse`（判"这批消息值不值得惊动模型"的那一处，`scheduleWake` 与 `wake` 共用）从 `getConfig()` 改成 `this.configFor(chatKey)`，并把那份配置交给 `responseConfigForChat(chatKey, cfg)`（那个函数因此多了一个 `source` 参数，缺省仍是全局那份，既有调用点逐字不变）。跑团用它把被接管的会话**覆盖成 4 档**（滑条 100 = 全部响应）—— ⚠️ 这一项与那三个宽度旋钮的取舍**相反**：100 已经是滑条最右端，没有"比它更宽"可言，所以它是覆盖而不是下限。探针实测：把读取点退回全局读 → `t-trpg` 红 1 条（**只有端到端那条**，`t-reply` 那条传的是显式配置、照样绿）。**往这张单子上加一项的办法永远是改那个读取点**，不是在这一侧多写一行补丁。
- **装载期对账**：`configPatch('')` 返回非对象、或那次调用抛错 → **拒绝装载**（与 `prompt` / `toolsFor` 同一条）。装载时另记一行日志说明"这个扩展会覆盖运行期配置" —— 判断"这个群为什么和设置里不一样"时，那是唯一的线索。

守护分两层，**缺一层就会漏掉一整类错误**（探针实测）：`t-reply.mjs` 逐项断言那几个帮手认传进来的那份（住在四个不同帮手里的配置项各一条：表情档位 / 统一字符预算 / 摘要档位 / 响应档位），`t-extras.mjs` 用**源级断言**钉 `agent-runner` 真的把它交给了两个 builder。删掉 `buildSystemPrompt({ config })` 那一行，`t-reply` 70 条**全绿**，只有源级那条红 —— "每处函数都对，但没人传给它"。



## 4. 装载与卸载

```text
/能力 加载 <id>   ── 闸门 → import() → 校验名字集合 → 记入装载表 → 起空闲计时器
敲扩展自己的命令   ── **不装载**：没装载就抛一句「先 /能力 加载」（消息照常落成已读）
每次执行          ── inFlight++ / 清空闲计时器 → 执行 → inFlight-- / 按 idleUnloadMs 重新起表
空闲到点          ── inFlight>0 就推迟；否则 dispose() → 从装载表删掉
/能力 卸载 <id>   ── 在途时拒绝；否则清计时器 → dispose() → 从装载表删掉
app.stop()        ── 清全部计时器 + dispose 全部已装载项（每个带等待上限）
```

- **TTL 是滑动的空闲窗口**，每次执行都把它推后。
- **在途调用期间绝不 dispose** —— 那是"任务跑一半被抽掉子进程"的成因，且症状偶发、看起来像扩展自己有 bug。
- **`dispose()` 有等待上限**（3s，且只在返回 thenable 时才建计时器）：一个卡住的扩展不该挂死 `stopLifecycle`。
- **装载闸门**复用 `media/call-budget.ts` 的 `SlidingWindowBudget`，键是**扩展 id**（防的是"反复起停同一个子进程"，那是速率问题，与哪个群在问无关）；被拒的那一次不占额度、也不加载。

## 5. 系统提示词：具名段落 + 框架契约

`buildSystemPrompt` 按 `core/prompt-catalog.ts` 的 `SYSTEM_SECTION_IDS` 拼段落 —— **段序即数组顺序**。有了段名，扩展才能"按名字覆盖"。

```ts
export const SYSTEM_SECTION_IDS = [
  'identity', 'persona', 'security', 'toolProtocol',
  'capabilityProtocol',        // ← 主流程那几个能力的用法（**不是**框架契约）
  'antiAiFlavor', …
] as const;
/** 框架契约段：接管模式下强制保留，且任何模式都不许被扩展 override。 */
export const SYSTEM_FRAMEWORK_SECTIONS = ['security', 'toolProtocol'] as const;
```

- **附加**：内置全段 → 按段名应用 `override`（空串 = 抹掉该段）→ 末尾接 `append`。追加放**末尾**，是为了前缀缓存能命中到追加点之前。
- **接管**：只剩框架契约两段 + 扩展的 `body`。

**框架契约两段为什么动不得**：它们不是"功能"，是**运行契约**。没有 `security`，扩展一句"你可以读本机文件"就把项目最硬的边界拆了（而它多半不是故意的）；没有 `toolProtocol`，模型不知道怎么发工具 JSON、怎么才算"说过话了"，整个 agent 循环当场失效。**两层守护**：装载时校验（拒绝装载）+ 拼装时跳过（第二道，防计划从别处拼出来）。

**（2026-10-15 补）分段的判据是"接管时该不该让它消失"，不是"它算不算重要"**：原先把"某个**能力**的用法"（漫画搜索/下载、转写、出图四条）也塞在 `toolProtocol` 里，于是接管会话必然带着一串"调用 `download_jmcomic`"的指令，而那个工具**不在接管者的表里** —— 模型调一次、拿一句"未知工具"、再重试一次。拆出去之后：

- `toolProtocol` 只讲 **agent 循环本身的协议**（无跨运行记忆 / 文本不发出去 / 参数是 JSON / 怎么算收尾），换一套人格它照样成立 ⇒ 框架契约，任何模式都保留；
- `capabilityProtocol` 讲**主流程那几个能力**的用法 ⇒ 不是框架契约，**接管时自动让位**，也因此可以被扩展按段名覆盖（那是它的正当用法）。

**往 `toolProtocol` 里加"某个工具的用法"就等于把它变成框架契约，接管扩展再也甩不掉它。** 工具用法一律进 `capabilityProtocol`。

**框架段的工具名是参数**（(2026-10-15)）：`toolProtocol` 第 2 条要写「要发言必须调用 X」，而接管会话里内置工具整体让位 —— 缺省那个 `send_message` 不在表里。所以签名是 `toolProtocol({ sendTool, finishTool })`，接管扩展在 `spec.overrideTools` 里声明自己那两个工具叫什么，`ExtrasRuntime.promptPlan()` 经 `PromptPlan` 的 override 分支带进 `buildSystemPrompt`。

三条判据都拦在**装配期**（`validateRegistry`，构造函数抛错），因为它们的症状都是安静的（模型调一次拿到"未知工具"再重试，群里迟一轮才见到话）：

| 判据 | 为什么 |
|---|---|
| `mode: 'override'` **必须**声明 `overrideTools.sendTool` | 不声明就照默认的 `send_message` 写，而那个工具不在表里 —— 接管者必然说不出一句话 |
| 声明的名字必须**真的在本扩展的 `tools` 里** | 与 `checkRuntimeShape` 同一类：声明与实现分居两处是这套设计唯一的漂移点 |
| 非接管模式**不许**写 `overrideTools` | 没有任何地方读它，纯属让下一个人以为它生效了 |

`finishTool: null` 是合法取值（本扩展没有收尾工具）—— 框架段第 5 条就不提它，**不提比提一个不存在的名字好**。

**重构的安全网**：原实现是"匿名数组 + `''` 分隔 + `join('\n')`"，新实现是"段名 → 正文 + `join('\n\n')`"。两者**逐字等价**，改造当次用一次性脚本对着 HEAD 版跑过 8 组配置（缺省 / 有人设 / 有自定义规则 / 空白人设 / 能力开关 / 收藏夹 / 走配置含 sticker 档位），全部逐字相同。

⚠️ 但**别只靠"段序断言"**：实测把 `join('\n\n')` 改成 `join('\n')`，全部 59 条断言**照样绿**（段序用的是 `indexOf` 递增，单换行也递增）。所以 `t-reply.mjs` 里另有一条**专钉分隔符**的断言。

**贡献随装载状态变化**（装载后出现、卸载后消失）。它**不是**"对话中途变"：`runAgent` 开头拼一次、整个工具循环都用它 —— 真实语义是"装载后，下一次运行生效"。

文案只许写在 `extra/prompts.ts`（模型可见的固定指令的唯一落点），那里有**三张表**：`EXTRA_PROMPT_TEXT`（按**工具名**索引，每轮进请求前缀）、`EXTRA_PROMPT_SECTIONS`（按**扩展 id** 索引，往 system prompt 里加的段落）、`EXTRA_PROMPT_JOBS`（按**扩展 id** 索引，扩展**自己发起的一次模型调用**的指令 —— 既不是工具说明、也不是常驻段落，比如跑团"把任意文本整理成剧本格式"那一次 / 2026-10-16 加）。

**前两张要求与注册表逐个相等，JOBS 只要求子集**（判据见 §5.2）。三张表的动态部分一律**由调用方传进来**，不在表里拼字面量 —— 该文件零 import，拿不到 `MAX_SCENARIO_CHARS` 那些常量，写成字面量就是等它漂移。群友可见的文案（命令用法、回执）**不在这里** —— 它们跟命令的实现放在一起。

### 5.1 `prompt(chatKey)`：按会话渲染，且必须是全函数

（2026-10-15 补，随跑团一起落地。）签名是 `prompt?(chatKey: string): ExtraPromptContribution`。

**为什么要 `chatKey`**：接管是**按会话**的，同一个扩展完全可能同时接管好几个群，而各自的内容不一样 —— 跑团的状态卡就是那个例子（A 群的战役与 B 群的战役毫无关系）。没有这个参数，"按会话渲染"根本无从谈起。

**为什么必须是全函数**：装载时 `checkRuntimeShape` 会**空着会话调它一次**，只做段落名对账。`chatKey === ''` 抛错就等于**拒绝装载**，而症状会表现成"这个扩展装不上"，与提示词毫无关系 —— 那是最难查的一类因果错位。跑团的做法是让 `store.read('')` 返回 `null`、渲染出"还没有开局"那段，于是空会话也拿到一份合法贡献。没有按会话需求的扩展（clock）照旧写 `prompt(_chatKey)`。

**两个形状上的坑**：

- `body` 的**每个元素是一个段落**，而**空串会被滤掉**（`promptPlan()` 的 `.filter(text => text.trim())`）。想在段内留空行，要写成一整块带 `
` 的字符串，**不能**用 `''` 占位。
- **顺序即缓存**：稳定的部分（人格）放前面、每轮都变的部分（状态）放后面，system prompt 的公共前缀才能命中到变化点之前。反过来的话，同一场会话连着跑几轮会让**整段**系统提示每轮失效。这与 user prompt 的"稳定度降序"是同一条纪律。

## 6. 接管模式（**唯一按会话隔离的东西**）

`spec.mode: 'override'` 的扩展被装载后，**那个会话**的模型侧整体让位：工具表只剩它的、命令表只剩它的（**外加永远在的 `/能力`**）、system prompt 换成"框架契约 + 它的 body"。

**只换模型侧三样**：消息存档、上下文窗口、记忆、历史摘要、后台长期任务全部照常。

### 6.1 按会话隔离

**接管只作用于它绑定的那个会话** —— 在 A 群敲 `/能力 加载 <接管扩展>` 只接管 A 群，B 群照常。附加模式的扩展则是**全局**的（`enabled` + `/能力 加载`）。

所以三张表都**按会话算**：`toolDefs(chatKey)` / `commandDefs(chatKey)` / `promptPlan(chatKey)`，`chatKey` 从 `agent-runner` 与 ingest 一路传下来（`isCommandEntry` 也多收一个会话参数）。

**为什么值得这份复杂度**：一个"接管"的扩展提供的是一整套替代人格与能力集，而一个 bot 常常同时挂在好几个群上 —— 全局接管意味着开了它所有群一起变，没法只在一个群里试。

**绑定有两个来源**：

| 来源 | 生效 | 落盘 |
|---|---|---|
| 配置 `extras.override: { "group:123": "扩展id" }` | `start()` 时播种，**改完重启生效** | ✅ 静态数据 |
| 群里敲 `/能力 加载 <接管扩展>` | 立刻，**只在本会话** | ❌ 内存；重启后回到配置那一份 |

**两条都仍然由人决定** —— 模型一个装载入口都没有（§2）。

### 6.2 三条边界

- **同一个会话同时只允许一个接管者**（第二个接管被拒，回话里带怎么解）；不同会话互不相干，两个会话绑同一个扩展时**实现只装载一次**。
- **接管模式的命令只出现在被它接管的会话里**。漏了这条的话 B 群也敲得到它，而它一执行就撞上"接管要指定会话" —— 群友会以为那个能力在本群可用。
- **接管模式下其他附加扩展不生效**：接管者的提示词与工具集是一套自洽的东西，混进别人的工具会让"它写的提示词"与"模型看到的东西"对不上。`/能力` 的列表里如实标出被它接管的会话。

### 6.3 为什么接管由命令驱动、而不是一个全局配置项

最初设计的是"配置里选一个接管者 + 重启生效"，但那样接管扩展有个鸡生蛋 —— 它的工具/命令只在装载后才有，而装载又要靠调用它们触发。改成"人敲命令装载即接管"之后，装载入口、接管入口、卸载入口是同一条命令，就没有死锁了（而且 `/能力` 在任何模式下都在，卸载总有路）。

**配置那条路后来补回来了，但换成按会话的 map** —— 于是"开机就让某个群由某个扩展接管"可以静态表达，而"临时在这个群里试一下"仍然敲一条命令就行。两条路的语义完全一样，只是一个落盘、一个不落盘。

## 7. 分层与那条例外

```text
core(0) → llm/chat/qq/media(1) → stickers(2) → agent(3) → extra(4) → web(5)
```

- `extra → {core, media, chat, qq, agent}` ✅
- `web → extra` ✅（组装根 import 注册表与运行时）
- **`extra → web` ❌** —— 扩展不认识 web。这也是"扩展不能用 web 的形状（`Route` / `CommandEntry`）"的原因：要产出它们就得 import web，方向立刻成环。所以扩展按自己的形状声明命令，由 web 侧的适配器接进来。
- 反方向同理：`agent → extra` ❌，所以扩展的工具表与提示词计划都由 `web/app.ts` 递进 agent 层（`toolDefs` / `extraPrompt` 两个可选回调）。

**唯一例外是 `LAYER_ALLOW`**（`scripts/check-layers.mjs`）：`core/prompt-catalog.ts -> extra/prompts.js`，让扩展的提示词有一个单独的文件管，而目录继续转发它。

**它之所以敢开，全靠目标是个叶子模块**：`extra/prompts.ts` 自己不 import 任何东西，所以不成环。往那个文件里加一句 import，环就可能成立（core → extra → core），而 `tsc` 不一定报错、运行期也只在特定加载顺序下才炸。闸门自带守卫（**例外目标出现任何相对 import 直接报错**），`t-extras.mjs` 里另有一条同样的断言。两条都实测过：加一句 import 之后，`check-layers` 报"必须是叶子模块"，而 `t-extras.mjs` **直接 TDZ 崩掉**。

## 8. 被否掉的方案

### 8.1 模型按需加载（否，且是本轮推翻的）

第一版是"工具声明静态进表、模型首次调用即加载、空闲卸载"。它能工作，但**装载的控制权在模型手里** —— 模型随口一次工具调用就能起一个 Python 子进程。现在装载由人决定，代价是工具表变成运行期可变（多一次缓存打散），换来的是"这个能力什么时候开"是一件由人决定的事。

### 8.2 "丢一个文件就生效"的插件目录（否）

仓库已定的边界（不为业务方法引入字符串式动态调用或运行时热替换）+ 拿不到 tsc 类型检查 + `scripts/build-desktop.mjs` 的 `APP_ENTRIES` 对账看不见它 —— 症状是"某个扩展没被搬进包"，而那正是打包脚本存在的唯一理由。**"按需加载"在这里的含义是"什么时候执行 import"，不是"import 什么"**：说明符永远是字面量。

### 8.3 整段后处理钩子 `transform(text) => text`（否）

最灵活（能条件注入、能删段），但也最难查：提示词变成拼不回去的一团，而缓存与段序断言都失去意义。具名段落是"具体、可审计"的那一侧。

## 9. 已知代价

- **模块代码不会被卸载**：Node ESM 没有模块卸载，`import()` 缓存永驻。没有 `dispose()` 的扩展，空闲卸载等于什么都没做。
- **工具表不再恒定**：装载/卸载各打散一次提示词缓存（频次由人控制）。
- **`extras.enabled` / `idleUnloadMs` / `maxLoadsPerHour` 都是保存后立即生效**（判据每次现读）；真正要重启的只有 `extras.override`（`start()` 时播种）。设置页原先写的是"开关要重启"，那是错的（2026-10-19 实测纠正）。
- **白名单群里任何群友都能敲 `/能力`**（@ 只挡手滑，不是权限；见 §2 的开放问题）。
- **未加载的扩展，命令认得出但用不了**：这是一条有意的取舍 —— 命令若干脆不在表里，那条消息会静默地进 LLM。
- **接管是唯一按会话隔离的东西**：`toolDefs` / `commandDefs` / `promptPlan` / `isCommandEntry` 都多带一个会话参数，注入链上（`agent-runner` → `WakeScheduler` → `Orchestrator` → `web/app.ts`）一路传下去。
- **`LONG_TERM_TASKS` 里只有 `extras.runtime` 一行**，扩展自己的重资源在那张表里看不到（不是遗漏：它们由各自的 `dispose()` 释放，而 `dispose()` 由这一行统一调度）。
- **扩展命令若声明成与内置同样的文案**（如 `/画`）：内置先匹配，那条扩展命令是死代码。结构上遮蔽不了内置，有行为断言钉着。

## 11. 宿主口子与运行结束钩子（2026-10-16 补，随跑团的兜底建议一起落地）

`load(deps)` 收下 `ExtraRuntimeDeps`；`ExtraRuntime` 上多了一个可选的 `onRunEnd?(session)`。

### 11.1 `deliverNote(chatKey, note)` —— 把机器条目送进会话

扩展只说"这是一条什么、正文是什么"（`ExtraNote`），**怎么落库由宿主决定**：`web/app.ts` 把它接到 `store.appendTrpgNote` → `deliverAsyncResult`（落存档 → 入窗 → 通知面板），与另外三种异步回流走同一条链。

- **为什么是参数、不是让扩展自己 import**：那条链要碰 `ChatStore` 与 `Orchestrator`，而 `extra → agent` 是反向依赖（层级闸门会拦），组装是 `web/` 的活。
- **为什么它不是"发一条群消息"**：那等于绕开扩展自己的发言工具与 `recordSent` 那本账。它落的是一条**未读的机器条目**，让模型有机会开口 —— 与 `AGENTS.md` 的「工具不得代模型发言」是同一条。

### 11.2 `onRunEnd(session)` —— 一次 agent 运行结束了

收尾点是 `chat/sessions.ts` 的 `SessionRegistry.finish()`（一次运行**唯一**的收尾处）。三条边界：

- **判据是本会话此刻由谁接管**（`#overrideEntry`，与 `toolDefs` / `promptPlan` 同一处）。所以**附加模式的扩展永远收不到** —— 它们没有"这一轮"的概念；扩展被关掉（不重启）之后也一样收不到。
- **旁路语义**：接线走 `SessionRegistry` 的**构造参数回调**（照 `StickerManager({ onChange })` 的先例 —— 低层不 import 高层），由 `extras.runEnded(session)` 转给实现。扩展抛错只记一行日志、不往上抛，更不影响 `finish()` 的持久化与返回值。
- **`autoLoad: false`**：一次运行结束不是装载的理由；没装载就什么都不做。

⚠️ **写扩展的人要记住的一条**：钩子里任何"再唤醒一轮"的动作（跑团落的那条建议条目就会唤醒下一轮），都必须带一条"**这一轮是不是真人推动的**"守卫 —— 否则它自己触发自己，形成无限循环。跑团的判据是"触发批里存在真人消息"，而这条判据同时就是它的终止证明。

## 12. 已知缺口（知情取舍）

- ~~**`onRunEnd` 里产生的模型调用不进 token 账**~~（**2026-10-17 起已修**）。它发生在 `SessionRegistry.finish()` **之后**，而 `#persist` 对已结束的会话会**重复累加** `usage-today.json` —— 当初记下的修法就是给 `SessionRegistry` 加一个**只叠增量**的入口，`addExtraUsage(usage, at)` 就是这么来的（不碰 `runs`：这些调用不是一次 agent 运行，算进去会让面板上"每次花多少"失真；四个数全 0 时直接返回）。链子：`ExtraRuntimeDeps.recordUsage` → `web/app.ts` → `sessions.addExtraUsage`；扩展那侧只在拿到口子时才上报（缺省 = 不记账、调用照常）。2026-10-19 起跑团**自己发起的那些调用全在这条链上** —— `.rh` 的暗骰叙事、`onRunEnd` 的兜底建议，以及量级最大的那一处：抽取管线与单次格式整理（一份模组最多 6 次调用）。日志仍留着（账本只给总数，"这一片花了多少"只有日志答得上来）。
